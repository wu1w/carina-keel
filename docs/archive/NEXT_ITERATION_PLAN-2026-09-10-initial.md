# Carina 下一轮：从可持久化对话到可玩的生成式世界

日期：2026-09-10。状态：开发提案，未实施；不自动替换冻结的 PRD v0.5。

## 结论

目前交付的是世界包、工具调用管家和按回合生成短片的验证原型。它证明了部分状态可以保存，却没有建立「玩家行动 → 规则裁决 → 世界变化 → NPC 反应 → 可见反馈 → 新的选择」的闭环。继续围绕 look、提示词和视频播放打补丁，不能填上这一缺口。

保留现有包、模块分层、工具共用、HTTP 隔离渲染后端、双语基础。下一轮把产品验收从“数据还在”升级为“行动有后果，后果可见，返回后仍然成立”。管家应承担有边界的裁判与导演职责。

## 2. 为什么离预期很远

### A. 产品目标发生了偏移：最高优先级

PRD §5、§7、§12 的验收集中在过夜、迁移、MCP 与无渲染仍可运行；§6 明确砍掉世界心跳与 NPC 定时行动，§15 才考虑完整 UI。README 甚至把像素定义为插画。

这些选择适合基础设施一期，但用户现在要的是可交互的世界。旧验收即使全过，也不代表玩家知道该做什么、有操作感、能改变画面或愿意继续玩。交接文档建议的修镜头、修 caption、换大模型，都是局部延伸，没有纠正成功标准。

### B. 缺少可裁决的动作与状态：最高优先级

`src/schema/tool-io.ts` 的八工具偏向创作与存储；没有玩家动作解析、前置条件、资源消耗与统一效果提交。`run-go.ts` 只检查目标是 Place 就移动，没有相邻性或门锁约束。`remember` 追加 Claim 与文本，不会把花瓶属性改为 broken；图补丁也没有属性更新这一直接语义。

因此“花瓶碎了”可能只是记住一句话；拿取、修复、归还、NPC 拒绝等需要模型临场编排。生成世界还缺少创作者与玩家权限区别：玩家说自己拿到钥匙，不应该等价于系统认可钥匙已经归其所有。

### C. 管家会调用工具，但没有一致性控制协议：最高优先级

`src/steward/run-turn.ts` 组上下文后进入自由工具循环，工具逐个落盘。没有完整动作提案、规则校验、统一提交、世界版本和提交后核对；模板只是要求记忆、回忆和调用 look。提示词无法替代运行时不变量。

存储也未达到完整事件溯源：`src/world/events.ts` 的 projectChronicle 只恢复 Event 节点，不重放 spawn/relate 为完整领域状态；`WorldStore` 的图、记忆和日志分步写入。不能把“日志优先”的文档表述理解成已经具备事务与任意损坏恢复能力。

### D. 事实到像素的传递丢失了关键语义：最高优先级

`run-look.ts` 虽传 entities.props，但 sidecar `_entity_names` 只消费名字；对象外貌、破损状态、持有者及相互关系没有结构化编译到画面约束，依赖 LLM 的 style 自行补齐。N 跳相关子图也不等价于当前镜头可见集合。

sidecar 的 `_need_new_seed` 按 style 文本是否变化决定重建，`_bake_seed` 用时间随机种子重新文生图。换一种镜头描述，可能换掉整间房；沿用上一末帧则可能积累漂移。它没有稳定外观参考、相机锚点、实体画面映射或状态差异驱动的局部更新。

管家能接收 look 静帧，但目前没有显式核对“图上存在的人是否真的在画面里”、不合格图的降级或重试协议。不能把图像输入能力视作已经具备视觉一致性验证。

### E. 接入方式把世界模型压成了短片生成器：高优先级

默认一次 13 帧、8fps，约 1.6 秒播放内容；请求全部生成完才返回。sidecar 始终使用同一个 `action_path=ACTION`；玩家移动没有转成动作序列，camera 也没有成为受控位姿。跨请求主要续上一 JPEG，没有应用级流会话与动作队列。

LLM 工具等待渲染，HTTP 渲染最多等待 300 秒，浏览器在整轮 SSE 完成前禁用发送。更快或更大的模型可能改善画质和等待，却不会自动补出控制、玩法或一致性。

官方仓库明确区分推理代码与实时部署，说明不计划发布自身部署代码，并提供其他部署参考。因此官方演示能力不能直接当作本机 1.3B sidecar 的能力。来源：[LingBot-World v2 官方 README](https://github.com/Robbyant/lingbot-world-v2#deployment)，核查于 2026-09-10。

### F. 没有设计可以玩的内容，测试也没衡量它：高优先级

当前页面只有场景图和聊天输入，没有目标、出口、可操作对象、背包或 NPC 行为提示。存档中的精灵主要是用户直接描述后生成的角色，不具备程序定义的目标和行动周期。玩家同时承担导演、内容作者和测试员。

`src/world/overnight.test.ts` 直接调用 remember 并断言文本保存，没有经真实 LLM 检查自主回忆，也没有检查花瓶变更、修复约束和画面。现有测试值得保留，但不能据此宣称游戏体验已经验收。

附带的长期问题：MEMORY 只追加，而 assemble-slices 取头部；编年只读取今昨。较新的关键事实在长时间使用后有被预算挤出的风险。需要按动作与实体检索有效事实，处理旧事实被新状态取代。

## 3. 下一版产品形态

目标：一个可以连续玩 10–15 分钟、可返回、可以自由表达行动的湖边酒馆世界切片。以场景为主屏，支持点击对象、选择动作、相邻区域移动和自由输入。回合推进规则、NPC 和剧情，界面即时响应，生成画面异步跟上。

这一步选择有明确空间锚点的场景探索；连续第一人称自由移动仍是目标方向，但必须先通过后端控制与延迟验证，不能把异步短片包装成实时操控。

### 可玩样板

三个区域：大厅、露台、储藏间。两个有不同目的的 NPC：老板与精灵旅人。六类可交互物件：杯子、花瓶、钥匙、账本、门、货箱。

开场事件：精灵寻找失物，老板隐瞒一笔交易。玩家可以询问、查看线索、交换物品、协助或破坏。两条完成路径；一次受阻后仍有替代线索。打碎花瓶会产生破损、NPC 态度与赔偿后果；修复需要材料或代价。离开回来后果仍在。

固定的是局部空间、规则和关键事实。LLM 生成对话、线索表现和受约束的剧情变体。既不要求无限世界，也不把整个体验写成固定对话树。

## 4. 管家与运行时如何分工

建议流程：输入/点击 → ActionIntent → Steward 提案 → Runtime 校验并提交 → 新状态与可用行动立即返回 → NPC 回应与叙事 → RenderPlan → 异步生成 → 验证后展示。

- **运行时**掌管事实：位置、物品归属、门锁、耐久状态、任务进度、世界时钟。规则验证目标存在、可达、可见、资源足够、唯一所有权和状态转换合法。
- **管家 LLM**解释自然语言，提出受类型约束的效果与 NPC 意图；根据已提交状态叙事；安排下一步有意义的选择。失败时说明原因并给替代行动。
- **导演职责**输出变化清单、镜头约束与必须保留的实体。初期仍由同一个 LLM 分阶段完成，不额外搭多 Agent 框架。
- **视觉观察**输出候选观察与置信度。像素不能直接覆盖权威状态；新增可交互对象要经管家和规则验证，再登记到世界。关键对象缺失或外貌冲突时，保留已验证画面或展示状态覆盖层，并明确画面尚未同步。
- **NPC**先随玩家动作推进一次 tick，具备目的、可知信息、位置和行为条件；不需要每秒调用 LLM。墙钟自动运行延后，先做确定可重放的行动时钟。

保留七类本体可承载这一切：给现有 props 增加有 schema 的字段；不要无节制新增节点类型。但要修改“八工具永久冻结、Renderer 只有单次函数、无世界推进、完整 UI 后置”的约束。

建议增加受校验的 `act` 入口；原 spawn/relate 等保留作创作/兼容入口。所有写入口必须服从同一个写入协议，先确定一个包的单一写入进程，避免 MCP/CLI/HTTP 各持旧图。

每次行动带 actionId、expectedRevision；一次提交记录完整状态差异和结果，可幂等重试。日志是可恢复的提交记录，图与 MEMORY 是投影。旧 v0 包先备份，再按明确版本迁移，保留原始编年。

RenderPlan 至少包含 worldId、revision、placeId、cameraAnchor、visibleEntities、canonicalAppearance、stateDelta、references、mustPreserve。RenderResult 回传相同 revision 和引用信息；旧结果不可覆盖较新状态。

## 5. 下一轮排期与交付顺序

按单人全职估算 20 个工作日；模型适配失败可能改变媒体方案。以下是提案工期与目标，不是已实现能力。

### M0 / 第 1–2 天：确定验收与查清控制上限

交付：PRD v0.6 草案、固定世界样板、六个玩家故事、完整链路计时与动作试验报告。稳定保存当前工作区基线与演示包到持久目录；是否提交由正常开发流程决定。

用同一场景分别验证左/右转、前进、人物进入、物品状态变化与返回镜头；拆开记录 LLM、规则、排队、生成、首帧与播放时延。核对当前 LingBot 动作格式、跨块/跨请求状态是否可继续，以及目标硬件实际能力。不能只测“成功返回 JPEG”。

关口：若无法可靠控制动作或返回同一空间，本轮使用固定相机锚点与生成关键帧推进体验，视频仅用于通过验证的过渡；明确自由移动仍未交付。避免先花数周重写 UI，最后才发现控制后端不可用。

### M1 / 第 3–7 天：动作和事实可信

模块：schema/world/tools/steward。

交付：move、inspect、talk、take、give、use、break/repair、wait 的动作契约；类型化状态、前置条件、动作 tick、提案/验证/提交；唯一写入、revision、幂等与恢复；存档版本迁移。

验收：不能隔空取物或无钥匙开锁；打碎与修复更改同一对象；重试不重复扣物品；失败不出现半个动作；从快照与已提交事件能恢复同一状态。模型不可用时，确定性按钮动作仍能完成。

### M2 / 第 8–11 天：能玩起来的场景界面

模块：server/public 与场景状态 API；实际开发时再选合适的前端组织方式。

交付：场景主屏、对象列表/经校验热点、动作菜单、出口、背包、目标、NPC 对话；自由输入同样进入 act；规则提交与媒体生成解耦。热点只能锚定验证过的对象，不能在任意漂移图片上盲放坐标。

把酒馆的两条路径和阻碍/恢复接到真实状态。加载与重连恢复当前地点、目标、对象和最近结果，避免已有世界仍显示“说第一句话”。

验收：不输入提示词、不懂工具的玩家能开始并完成一条路径；画面生成中仍能查看信息、选择后续行动，状态修改按序执行。

### M3 / 第 12–16 天：让可见世界跟随事实

模块：render/sidecars/steward/server。

交付：Scene/RenderPlan 编译、稳定人物/场景参考、相机锚点、按变化选择更新策略；媒体异步任务、revision 丢弃旧结果、取消/超时、可见降级；先验证关键帧，再启用受控短片过渡。

换镜头不得默认随机重造场景。固定随机种子只能提高复现性，不足以保证人物和布局一致；参考图与受约束更新必须实测。简单名字提示词不能当最终方案。

验收：指定人物出现、物品变化可见、返回位置可辨认；关键状态检查不通过的画面不能作为已同步现场静默展示。若候选模型做不到，按 M0 关口收窄画面承诺并记录未完成项。

### M4 / 第 17–20 天：连续性与玩家验收

交付：按动作/实体检索有效记忆、旧事实替代规则、NPC 知识边界；长回合、重启、跨目录、模型失败、重复请求和旧帧回流测试；真实模型与人工体验报告。

验收不再用测试数量代替体验。至少 3 位未读代码的试玩家完成路径；记录在哪一步不知道做什么、等待退出或发现矛盾。

## 6. 必须通过的六个故事

1. **可发现与可操作**：新玩家进入酒馆，60 秒内不靠开发者讲解执行有意义的动作；这只是目标，尚未实测。
2. **行动有代价**：无钥匙不能开门；交出钥匙后背包失去同一把钥匙，对方获得它。
3. **人物是同一个人**：精灵进入、交谈、离开、返回时 ID、姓名、外观参考与记忆一致。
4. **物品变化可见且持久**：打碎花瓶 → NPC 反应 → 离开 → 重启 → 返回，仍碎；修复有前置条件，修复后过时记忆不再当现状。
5. **选择导致不同后果**：至少两条完成路径，一条被阻断仍能找到替代，NPC 不泄漏未知信息。
6. **慢模型不冻结游戏**：渲染失败、重复点击、断线重连、旧画面晚到，都不重复动作或回退已提交状态。

测量目标：本地交互反馈 p95 ≤100ms；确定性动作提交 p95 ≤500ms；LLM 实质回应 p95 ≤5s（单独测量，不把“正在思考”算回应）。收集至少 100 次操作，声明硬件、模型、并发和冷/热条件。达不到就降低调用依赖或调整承诺。

视觉验收：预先固定 20 个镜头检查点，关键实体、归属和破损等硬事实不得矛盾，人物/空间参考一致通过率目标 ≥90%，失败点须有明确降级。人工标签配合独立视觉检查，不能只让生成叙事的同一模型自评。确定性规则的固定测试集要求全部通过；真实 LLM 另跑至少 3 组 30 回合测试，记录每次矛盾，不能拿固定测试通过率代表开放世界可靠性。

## 7. 暂缓与第一批任务

本轮暂缓无限地图、多人、多模型商城、Skill 市场、复杂战斗与全面 3D 重建。也不先购买更大 GPU：先做控制与延迟测量，确认瓶颈后再决定后端投入。

第一批可以直接拆成三个开发任务：① PRD 与样板/控制试验（M0）；② act + 提案/提交 + 状态恢复（M1）；③ 场景操作 UI + 异步媒体与版本契约（M2–M3，M1 契约稳定后推进）。每个任务必须带玩家故事和验收脚本。

本次只新增分析与计划，没有修改运行时代码、演示存档、远端服务或提交现有改动。
