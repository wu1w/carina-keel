# 游戏式交互专项检查

日期：2026-09-10。检查范围：最新工作区代码、本机运行服务、aiga 的实际 sidecar 文件与推理实现。本文是改进建议，没有修改业务代码、切换世界、发送生成请求或重启服务。

## 1. 结论

等待的首要原因是控制路径：有生成画面时，前端停用本地移动/相机与 WebGL 场景显示，将输入转换成视频生成任务。当前真实世界还没有对应的三维场景。仅增加流式传输、换快 LLM 或缩短视频，都不足以获得游戏操作感。

应把每帧交互交给本地三维运行时，把管家与世界模型放到异步内容生产路径。自然语言仍负责世界创建、目标、规则、编辑与剧情；键鼠和已经解析的导航目标直接驱动运行时。

- 正在服务的 HTML 包含 hasGeneratedView、requestTour 和关闭本地移动的分支。完整 HTML 与源模板的字节差异包含启动数据注入，不能据此判断部署过期。

## 3. 根因与代码位置

### P0：生成图片出现后，立即失去本地操控

`src/server/public/app.html`：

- 1849：只有 moving && !hasGeneratedView() 才执行 stepPlayer。
- 1921：hasGeneratedView 由图片 visible 或 stillReady 决定，连恢复的静帧也会触发。
- 1979–2038：WASD → maybeTour → requestTour → generation.start/observeOnly，等整轮结果后才应用画面。
- 2541、2552：右键拖动有图时不改相机；松开后转换成 pan/tilt 提示词并生成。
- 1558：drawGl 在有图时提前返回，已有 WebGL 路径被屏蔽。

应引入明确 viewportMode（play/preview/inspect），与是否加载图片分开。play 的输入始终直接操作真实场景；preview 可以独立查看候选，不得自动抢占游戏相机。不能只删除条件就宣称修好：当前真实世界为空，必须先提供实际可用空间。

### P0：图像生成与空间生成仍然分离

`src/application/create-application.ts:474` 的 handleCreate 只在没有 observe 后端时调用 runGeneration；连接真实画面后端时直接走观测。因此当前真实世界可以只有图像、没有 regions/objects。

`src/application/load-deps.ts:504` 的空间 provider 包装仍调用 mock。`src/spatial/bake-map.ts` 将现有对象网格化，并把静帧绑作贴图；`object-mesh.ts` 主要使用 AABB，pickup 使用程序杯子网格。这些是有用的代理资产，但没有恢复画面中的真实布局。

以 viewable/playable 进入条件约束产品流程：创建后先 preview；获得验证过的空间后允许 play。空间获取可以是真实三维生成导出，也可以是受控多视角重建；不能把 preset+投影贴图标记为已恢复原场景。

### P0：长推理占用世界串行队列

`create-application.ts:199,378` 的 dispatch/enqueue 将普通世界命令交同一个 SerialQueue；`runObservation:1533` 内 await 完整 observe；`v1-session-routes.ts` 的 control 路由最终也走 dispatchCommand。

因此“独立控制 URL”尚不等于真正的高优先级控制。前一个生成未结束，后面的 pause/普通动作可能排队。暂停后防旧帧的校验也不能解决暂停本身迟迟执行的问题。

改为：短提交队列只用于状态提交；长生成启动后立即返回 jobId；任务完成后带版本/epoch 回队列验证。pause、stop、输入更新走独立运行时控制入口，生成失败不影响已知空间的游玩。

### P1：输入同步与碰撞不一致

`app.html:1792` 的 queueMove 每 180ms 发一次绝对位置命令，无序列确认，响应也未用于纠正。syncCamFromRuntime 在误差超过 2.5m 才修正，容易产生“能看到但状态没跟上”或突然跳回。

前端 mapColliders 仅根据 roomBounds 构造四面墙，不能表达权威场景中的门、家具与不同区域。应共享碰撞资产与移动规则。

建议本地即时预测，发送 inputSeq、按键状态、朝向、controlEpoch；服务端固定 tick 返回 lastProcessedSeq 与权威位置。客户端重放未确认输入、小误差平滑校正。高频输入只保留最新状态，不能积压成逐次视频请求。松键/失焦/暂停都清空输入。

### P1：sidecar 是批处理短片服务

`sidecars/lingbot-still/server.py:296` 使用固定 ACTION 调 generate；Camera 字段主要进入提示词，未转成 poses.npy。`do_POST` 持全局 LOCK，完整视频生成、CPU 转 JPEG/base64 后才响应。HTTP renderer 等待上限 300s，前端 requestTour 等待上限 320s。

取消客户端请求不代表停止 GPU 计算；增加 WebSocket 也不会改变这条批处理推理路径。即便继续研究视频直接驱动画面，也需要真实相机控制、跨块状态、增量解码、输出回调、最新输入与中断边界，并单独验证时延。

### P1：待机已改善，但仍不应负责主视口生命感

本轮已加入 50ms 仿真循环、至少 30s 的 idle 请求间隔、失败退避与过期校验；上一轮“没有独立时钟/每50ms待机请求”的描述已过时。

保留这些改进。运行时负责火焰、水面、人物待机/移动等显示与行为；低频模型只决定新事件或生产新资源。无需为“玩家没动”持续支付整幅画面生成成本。仿真循环内 await persistRuntime 仍可能造成 tick 抖动，应测量并让快照持久化脱离时间推进路径。

## 4. 目标执行结构

### 输入与显示路径（每帧）

键鼠 → 本地输入状态 → 角色控制/碰撞预测 → 相机 → 已提交三维场景渲染。

这一条不得调用 LLM、世界模型、全量导出或磁盘快照。自然语言“走到吧台”只在初次解析目标时等待，之后导航由运行时连续执行，并能立即中断。

### 仿真与校正路径（固定 tick）

最新输入 → 权威运行时 → NPC/交互 → 序列确认与状态增量 → 客户端插值/纠正。快照定时异步保存，关键物品/编辑提交使用持久事务。

现有 20Hz 可作为起点，按视觉和碰撞需求评估；不必先追求更高频率。保持本地优先运行，GPU 远端不进入键鼠反馈链。

### 内容生产路径（秒到分钟）

玩家接近边界或管家决定事件 → 按世界记忆生成候选 → 几何/对象校准 → 校验 → 分块提交 → 运行时加载。

准备距离由玩家速度与实测生成/校准延迟决定。在玩家抵达之前完成下一空间；没准备好保留可解释边界，不能停住整个相机。待生成区预览与已提交空间显示明确分开。

## 5. 空间资源路线

即时移动要求任意相机位姿下可以得到画面。单张图片只有一个视角；把它投影到盒子上只能在有限范围产生近似视差，侧面/遮挡后面会拉伸或缺失。增加杯子细节、后处理或插帧不能补出房间几何。

优先验证一个真实生成房间的可视网格或 splat+碰撞方案，独立对象使用真实 mesh。需要建模导出时最终必须有可视 mesh；背景 splat 与 collider 不代表编辑资产完成。

若走视频重建，采集受控平移/重叠视角，保持静态背景一致；保存真实或估计相机、尺度锚点与置信度。先做小房间再扩展，不承诺由当前轻微运动的 13 帧恢复整座世界。

离线代理场景可用于验证手感，但报告中必须标注它不是最终生成世界。把“输入无等待”与“生成场景可准确固化”分成两个验收，避免为了画面好看重新退回按键发视频。

## 6. 实施顺序

### 第一步：先救输入链路（建议首个 2–4 日切片，估算）

- 明确 play/preview，移除 play 中键鼠 → requestTour 的路由；图片只作为参考/预览或场景纹理。
- 保留现有 WebGL 可用于短期验证；复杂 mesh、材质与资源生命周期再采用成熟渲染库，不先做全站重写。
- 长生成返回 jobId，不占用世界写队列；pause/stop独立入口。
- 输入序列、预测/确认、共享碰撞；开门/拿取只走确定性动作路径。

验收：使用有实际碰撞的基准房间，模型服务断开时转头、行走、停步、开门仍即时；后台生成中同样通过。此步只证明手感，不证明重建成功。

### 第二步：替换代理空间（独立技术关口，不预承诺工期）

从真实生成结果取得一个可导航的空间资产；验证六个视角、尺度、碰撞、三个独立对象、导出以及重启。失败就继续处理生成/重建后端，不能靠修改 frozen 标记通过。

### 第三步：让世界在后台生长

将 runExtensionLocked/接近门触发改为预取任务与短提交；加入并发限额、区域依赖、旧结果隔离和缓存。先完整实现“酒馆→花园→返回酒馆”，保护原空间引用。

### 第四步：单独评估实时神经视频路线

若仍要求整个主视口由 LingBot 实时输出，先测会话内动态轨迹、输入改变到首个对应帧、稳定生成吞吐和中断延迟；技术关口不通过，不把它放回基本操控路径。

官方代码支持因果分块与 KV caching，但官方演示不等于当前部署的能力。参考：[LingBot-World v2](https://github.com/Robbyant/lingbot-world-v2)。

## 7. 必须增加的验收

- 连续 WASD/鼠标操作 60 秒，在已知区域内 LLM 与世界生成调用数为 0。
- 后台任务持续时，pause/stop 接收至屏障生效目标 p95 <100ms；松键不会继续播放此前排队的前进动作。
- 指定设备上输入到第一帧变化目标 p95 <50ms，60fps 目标对应每帧约 16.7ms。均为目标，尚未实测。
- 人为使生成服务超时，仍可在已提交区域连续行走、交互。
- 客户端与服务端面对门、墙、家具使用相同碰撞数据，不依靠 >2.5m 后强制跳回纠错。
- 固化重开后检查真实场景外观与几何，不能只检查对象数量和哈希。
- 单独记录 input、first local frame、runtime ack、queue、LLM、GPU prefill/denoise/decode、media delivery 时间。日志内部进度条不可替代完整链路测量。

## 8. 现在应避免继续投入的方向

暂不继续优化按键对应的 prompt、增加更长视频缓存、用循环生成替代待机动画，或为每次动作加一个更快的 LLM。也不要只换传输协议期待获得实时性。先实现即时控制和有实际空间的主视口，再评估生成性能投入。
