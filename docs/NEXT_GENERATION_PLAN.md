# Carina 下一代开发方案：持久三维世界与后台生成

版本：NG-1，2026-09-11。状态：开发方案，未代表部署、画质或性能已达标。

实施已于2026-09-11启动，实际完成项与阻塞见[六阶段实施进度](development/P0_PROGRESS.md)，不要将本方案的目标当作当前能力。

本文收敛最近几轮讨论，作为下一轮实施顺序与技术路线的主入口；PRD v1.0 的世界 session、自然语言、空间记忆和导出要求继续有效。与旧文档冲突时，以本文的远程游戏主路径和阶段顺序为准。研究依据见 [SolarWM 审查](SOLARWM_REVIEW.md)，资产处理细节见 [酒馆流程](TAVERN_GENERATION_PIPELINE.md)。

## 1. 本轮决定

### 目标校正（2026-09-11，依据用户再次明确的产品目标）

产品主体始终是“能控制生成式世界模型、维持稳定世界并导出的Agent”，游戏式交互是体验要求。UE、Pixel Streaming、IoStore、PBR测试物件都是实现手段，单独完成不能代表产品进度。此前执行过度集中在渲染验证；以下闭环关口优先于第8节原本先完整打磨P1、再做P2/P3的严格串行顺序。原阶段内容保留，但生成、记忆、导出必须提前贯通，不能等待画质精修完成才接入。

下一项产品验收：用户自然语言创建一个小空间 → 真实世界模型产生带来源的区域/布局/外观候选 → 经几何验证、必要补全与校准形成规范空间表示 → 同一session中游戏式探索 → 自然语言修改一个对象或局部区域 → 保存、重开保持一致 → 导出GLB与贴图并在建模工具验证 → 以已提交空间约束生成相邻内容。

必须明确世界模型实际贡献和转换步骤。复用资产可以补齐结构和物件，但不能用LLM挑选资产库加场景组装代替全部世界模型生成，也不能把标准测试头盔当生成内容。视频输入若不能可靠恢复三维，则记录路线未通过，选择有证据的三维生成路径；不暗中降低为看视频或手工搭场景。

运行时以同一可移植SceneManifest/资产/对象身份为输入，Windows cooked包只是可重建缓存，不成为唯一世界真相。游戏移动走运行时，管家负责规划、校准、任务调度和记忆提交。保存与导出提前验证，生成服务离线后已固化区域仍可游玩；重开不能重新生成一份近似世界。

当前Windows支线继续完成最小可用PBR与通用资产入场接口，保持已有工作可复用；不继续增加仅用于截图的新测试关卡，也不让Mac网络或极致光照阻塞独立的生成—空间提交—导出工作。完整画质与性能目标保留在后续集成验收，不以粗模宣布最终完成。

交付一座可以真正走进去、修改、保存并扩展的高质量酒馆。稳定三维世界承担空间、物体和交互；生成模型持续提供候选资产、材质与区域；管家把自然语言变成有范围、有版本的世界修改。

正式显示路线转向 Windows RTX 5070 Ti 上的成熟游戏引擎，通过低延迟视频流在浏览器游玩。首选 UE5 + Pixel Streaming，先通过实际设备验证，再锁定引擎、插件和部署版本。当前 WebGL 粗模降为诊断/布局预览；不再沿它持续自研高质量渲染器，也不同时开发两套正式视口。

首发画质依赖完整资产、PBR、阴影、间接光、反射与稳定的时间表现。Lumen 是首选验证项，DLSS 超分是可选优化；DLSS5 神经渲染、逐帧世界模型增强和 SolarWM 推理不成为发布前置条件。光栅、光追和重建按实际开销组合，不能认为换成光追会自动得到好材质。

首次交付范围：一个活跃世界、约 12×10 米酒馆、一个相邻庭院，再扩展一个小区域。允许多个持久 session；暂缓多人、无边界地图、完整战斗、通用动画生成和训练基础模型。

## 2. 当前实现与根因

2026-09-11 检查代码和本地服务文档，未重新做 GPU 或画面实测：

- `src/server/public/app.html` 的场景绘制仍把 u_texOn 设为 0；简易着色路径不能承担目标 PBR 画质。参数化几何和颜色规则无法提供可信的近景资产细节。
- `src/world-scene/` 已有组装与区块基础，但粗模扩展数量不等于可用内容增加。更积极调用视频模型也不能消除视角切换时的几何跳变。
- `src/sessions/`、`src/pack/`、`src/spatial/`、`src/jobs/`、`src/runtime/` 已有代码与测试，作为审计和复用对象，不按目录存在就认定端到端完成。
- Windows API 文档已描述资产上传和 assetId；本地 graphics-service.ts 仍要求 scene_glb。前后端契约需要统一。文档中还保留旧绝对路径例子，必须随联调清理。
- Windows 当前接口是离线帧/文件验证方式；PNG 回读和任务轮询不适合玩家输入循环。Lumen、DLSS NR 和实际串流能力仍须验证。

过去主要问题是将“模型生成出内容”“离线渲染能出图”“主视口可高质量游玩”当成同一项能力验收。下一轮拆开验收，但最后必须在同一个产品入口合起来。

## 3. 用户体验

用户输入：“创建雨夜湖边酒馆，暖色壁炉、旧木吧台，能走到吧台后面。”

准备期完成布局、关键资产、照明和通路检查；显示真实阶段进度与已有参考，不用参考视频冒充可玩画面。准备完成后明确进入，首屏关键资产不能靠色块占位。

进入后，键鼠直接控制 Windows 游戏运行时，连续转头、移动、碰撞不经过 LLM。管家同时接受“把吧台右移半米”“木头旧一些”“门外增加露台”。可确定的空间修改直接形成事务；需生成的部分异步完成。自然语言“带我走到门口”编译为导航目标，由运行时执行，不逐步问模型。

已生成并提交的区域持续保存。走出酒馆再回来，杯子、桌子、门状态保持；生成服务停止仍可游玩已固化区域。此处指生成服务离线，不意味着关闭 Windows 渲染主机后浏览器仍能游玩。

暂停世界冻结模拟时钟与行为，观察和编辑仍可用；停止生成单独控制后台任务。暂停期间不自动发布区域，明确的编辑事务可以提交。切换 session 保存检查点并释放旧世界输入，晚到任务不能修改新世界。

## 4. 系统架构与模块

### 4.1 Web 客户端与远程游玩

负责世界列表、串流显示、键鼠捕获、对象选择、管家对话、准备进度、保存/导出。现有 app.html 逐步拆为可构建模块，保留现有业务入口。

浏览器输入通过实时通道到运行时；序号、失焦释放、断连释放和重连状态同步必须实现。媒体连接绑定经过认证的活跃世界，不允许仅凭 worldId 取得控制权。先局域网单客户端，不扩展公网部署范围。

新增建议目录 `src/play/`：运行时连接、会话租约、状态镜像和协议；`src/server/` 保持业务 API 门面。视频信令和游戏控制不复用慢速任务轮询。

### 4.2 Windows 游戏运行时

新增建议目录 `runtimes/unreal/`，独立打包与版本管理。负责相机、角色控制器、碰撞、导航、对象交互、PBR/光照、资源流送和硬件编码。

采用成熟引擎的控制器与物理能力；用数据驱动行为模板实现门、杯子和简单 NPC。管家输出受约束的行为参数或规则，不在运行时任意生成并执行状态机代码。

UE 的 GLB 运行时导入、材质映射、碰撞创建和打包必须列为技术关口。编辑器能导入不等于打包应用能热加载。若需要异步 cook，则产物同时保存可移植源资产和引擎包，测量 cook 时间，不能每次加杯子都重打包整个应用。

### 4.3 世界与管家控制面

复用并审计 sessions、application、steward、pack、spatial。世界包保存权威的已提交空间版本、对象身份、语义、规则、资产和历史；游戏运行时持有运行期间的权威实时运动状态。

两者不争抢写入权：运行时固定步进执行、输出事件和检查点；结构编辑通过唯一事务协调器提交。由暂停屏障或安全帧边界安装新 revision，再确认运行时已应用。崩溃后从最近检查点与事件恢复，不能用旧浏览器相机覆盖服务端状态。

### 4.4 场景编译与资产目录

SceneSpec 描述风格、米制空间、锚点、连接关系、通路、物件和光源意图。编译器输出 AssetPlan，按“复用合格资产 → 改造已有资产 → 新生成特色资产”路由。

建筑用有厚度、倒角和 PBR 的模块件组装；高频物件实例化；特色物件真实生成。目录按 assetKey、尺寸、风格、质量、来源检索，统一材质族和纹理密度。复用资产与现场生成分别记录，不能把资产库组装全部称为生成。

新增建议目录 `src/scene-compiler/`、`src/assets/`，避免让 world-scene 的粗模配方承担全部资产语义。

### 4.5 GPU 资产工作器

候选资产统一做单位/轴向、节点变换、枢轴、UV、法线切线、材质通道、碰撞、LOD 和导出验证。已有合格项目跳过处理，输出按内容哈希缓存。

生成贴图作为固定的表面资产使用：去光照、无缝处理、必要超分，然后在稳定 UV/坐标中绑定。窗影、高光不能直接当 baseColor；推断的材质通道要标记来源并验证。生成图里的气氛可转为光源意图，不能把图中亮斑等价为真实光源。

扩展 `src/providers/`、`src/jobs/`，重计算在独立 worker，业务 API 不加载 GPU 模型。所有上传/任务使用 assetId，返回完整 contentHash 校验；短 ID 碰撞必须检测。

### 4.6 区域扩展调度器

调度优先级：当前路径缺口 → 可能进入区域 → 可见远景 → 近景精修 → 可选装饰。利用朝向、速度、路网分叉、停留和用户目标预测，不只沿鼠标朝向生成。

候选阶段：planned → generating → validating → ready → committed → resident；失败、取消、过期独立记录。只有通过几何、材质、碰撞和预算检查的区域才可进入 committed。

### 4.7 空间记忆与导出

资产、对象和区域 revision 为持久记忆主体；检索参考图、深度与描述辅助模型理解，不能取代三维事实。再次生成读取已提交几何、相机、保护遮罩和对象锚点。

GLB + 贴图 + 对象/尺度/来源 manifest 为可移植交付；引擎专用缓存可重建。导出固定 revision，独立门和物件可在 Blender 选择编辑。不得只导出视频或 splat；允许 splat 作为非交互背景，但不得覆盖门、杯子等可交互对象。

## 5. 关键数据契约

沿用已有 schema 能表达的字段，缺失部分做显式迁移，不另造同义身份。

- WorldSession：worldId、activeRevision、runState、controlEpoch、runtimeLease、checkpoint。
- SceneManifest：米制/Y-up坐标约定、regionId/objectId、变换、assetHash、材质、碰撞、交互绑定、光照依赖。
- ObservationBundle：帧、相机内外参、深度及置信度、来源、生成/观测标记、几何检验结果。输入控制相机与从画面估计的相机分开保存。
- AssetArtifact：contentHash、source、portableGlb、纹理、collider、LOD、处理版本、validation、可选 engineArtifact。
- WorldPatch：commandId、worldId、expectedRevision、controlEpoch、readSet、writeSet、保护对象、资产依赖及撤销信息。
- Job：幂等键、输入哈希、阶段、进度、超时/重试次数、取消、峰值资源、产物哈希。幂等键包含后端版本与所有影响结果的参数。

发布协议：资产先持久化并校验 → runtime 预装候选 → 检查 revision/readSet/epoch → 帧边界原子激活 → 记录应用确认。失败保留上一版；超时后查询真实状态而非盲目重复提交。恢复过程必须覆盖发布各阶段崩溃。

## 6. 建模与生成共存的三层策略

第一层是已承诺空间：房屋结构、通路、碰撞、可交互对象和已确认材质稳定存在。它是游玩和导出的依据。

第二层是后台生成内容：模型扩展未探索区域，生成特色资产、材质和照明候选。通过检查后变成第一层。精修可在更早的可玩版本基础上继续，但关键首屏达到质量门槛才能入场。

第三层是可选神经显示增强：后续才试验深度/法线/运动矢量约束下的增强，单独测转头、遮挡、物体交互、HUD 与输入延迟。显示增强不是世界记忆，不能改变碰撞与对象位置，也不能用它掩盖错误资产。没有可信的实时后端时不做主路径。

SolarWM 优先放在第二层的观测处理和参考生成。限定实验额度：先已知相机视频校验真实数据引擎，再与现有模型同轨迹对照，再固化一个片段。关闭 dry-run；分别记录几何一致性、GPU 秒、显存、失败率与人工修复量。若 5B 不能在现有设备合理运行，先复用数据工具，不为它迁移整个系统。

## 7. 主动预生成与资源预算

初始化先准备可玩核心和至少一个相邻区域，之后允许进入；后台保持一个正在处理、一个已就绪区域作为起始策略。区域尺度按实际生成时延决定，不能把固定区块数量当开放世界能力。

提前量按实测估算：到达时间应大于生成、重建、资源上传/导入的 P95 总时间加安全余量。朝向快速变化时保留候选缓存，去重并限制重排，避免推理反复取消重启。无法赶上时保持既有区域完整，在边界提示准备状态，不能突然刷图或让玩家跌入未加载空间。

玩家无命令时，运行时继续火焰、雨、环境声和已编译行为；调度器在许可预算内扩展，达到就绪储备后停止重生成。后台不是无限循环调用模型。

5070 Ti 优先保障游戏渲染和编码。重生成/重建初始并发 1；以任务实测峰值显存加余量做准入，不能靠 CUDA 任务优先级假设可抢占长推理。帧耗时超标时在安全任务边界暂停或不启动新工作；若并存不可用，重任务限准备期，游玩期只做轻量组装和预加载，并明确尚未达到边玩边重生成目标。

Mac 负责控制面、元数据、缓存索引与 CPU 处理；其他已有 GPU 仅在后端兼容和传输成本实测后分担。MI210 不作为 DLSS/Lumen 的假定执行设备。CPU/GPU 转移、纹理解压和引擎上传也进入资源预算。

## 8. 分阶段开发与交付

按一个全职主开发者估算 45 个工作日，集成返工预留后约 10–12 周。是工作量区间，不是日历承诺；引擎安装、模型访问和未知重建问题会触发重估。第一周重点交付可评判的体验，不能等最终集成才展示。各阶段验收是继续投入的条件。

### P0：运行时与资产入口关口 / 3 日

锁定现有代码/资产可恢复基线与设备版本。用合格酒馆样板打通 Windows 打包运行时、浏览器输入及串流；完成单个 GLB 的打包后运行时导入或独立资产 cook/加载实验。统一资产上传和 assetId 契约。

交付：实际浏览器录屏、版本清单、分段耗时、导入材质检查、运行时 ADR。样板只证明渲染能力，不算真实生成链通过。

停止条件：不能在打包程序加载新资产、控制明显卡顿或画质仍不成立，先定位解决；3 日到期记录阻塞并重估，不以编辑器截图通过。UE 路线失败须给出证据后再选替代成熟运行时，不能静默回到粗模。

### P1：高质量可玩酒馆 / 7 日

实现完整 PBR、直接/间接光与反射、出生点、连续控制、碰撞、门和杯子；将真实串流接入原产品主视口，串流失效有明确状态。配置主光和环境、检查近景木材/金属/玻璃；固定相机、曝光和路线用于复核。

交付：10 分钟浏览器游玩记录、6 个固定视点和回看路线、无后台生成性能基线。关闭生成服务仍可运行。美术样板允许资产库组装，需标来源。

停止条件：用户仍认为画质粗糙或移动难受，不扩大地图，不增加模型数量；明确是哪类资产、材质、照明或控制问题，再修本阶段。

### P2：生成到建模资产工厂 / 10 日

实现 SceneSpec → AssetPlan → 处理/校验 → manifest → 引擎加载。至少一个特色物件真实生成入场，一种生成材质正确绑定；小资产库支持酒馆变化。完成独立 GLB 导出，验证材质、单位和对象拆分。

SolarWM 支线最多先投入 3 个开发日，包含在本阶段预算内；输出是否接入的实验结论，而非要求必须成功。失败使用已验证的复用/原生 3D 路径，保留视频重建未通过的结论。

交付：完整任务日志、原始与处理产物、相同需求重复生成样本、人工修复清单。不能把手工挑选最佳结果包装为全自动。

### P3：管家编辑与空间记忆 / 8 日

复用现有 session/事务/规则代码补齐运行时桥接，完成指代对象、局部移动、材质修改、暂停、撤销、恢复、两个世界切换与固定版本导出。

交付：至少 10 条固定自然语言任务的执行证据；桌子移动不改墙、杯子拿走不留背景副本，切换后旧任务不串台。验证崩溃发生在发布不同阶段时可恢复。

## 9. 验收标准与观测方法

以下均是拟定目标，尚未实测达成。

画质：酒馆整体与桌面/吧台/壁炉近景均有可信尺度、表面细节、阴影和反射；6 个固定视点无丢贴图、全场同一法线、穿帮与异常曝光。慢移、快速转身、反复遮挡无场景刷图和物体漂移。最终由用户实际浏览器试玩确认，不用模型美学评分替代。

手感：先 720p60 验证链路，正式目标 1080p60；固定路线连续 10 分钟，报告服务端帧时 P50/P95/P99、客户端显示帧率、丢帧及卡顿。初始帧时目标 P95≤20ms；输入到显示 LAN P50≤80ms、P95≤120ms。完整延迟用可校准高速录像测至少 100 次，代理指标单独标注；帧生成后的显示 FPS 不替代响应测量。

准备速度：暖缓存已固化世界重入目标≤10秒；资产库组装路线到可进入目标≤90秒，均包含运行时导入。特色资产首次生成与视频重建先报告实测分阶段时长，P2 才据样本确定预算，不虚构统一秒级承诺。

扩展：受控路线至少 10 次接近边界，起始目标≥90%到达前就绪，记录样本数并避免将小样本外推到任意探索。开启后台工作后仍按上述手感标准验收，不能只报告 GPU 工作器吞吐。

持久与导出：模型离线可走动/开门/拿杯；重进对象状态一致；两个世界隔离；至少门和三个物件独立可选；尺度锚点误差目标≤5cm；所有纹理离线可解析。引擎专用光照另附数据与限制，不能保证 GLB 还原引擎全部效果。

自动化检查覆盖契约、版本/幂等/取消、资产验证、运行时桥接和故障恢复；实际模型、材质、控制和视频链路做集成与人工验证。每阶段执行与改动相关的测试，文档更新不重复跑整个项目测试。
