# 高质量酒馆：生成、建模、游玩的一体化验证流程

日期：2026-09-11。状态：已确定的下一轮设计与验收方案；不是已实现能力或性能承诺。

最新实施顺序以[下一代开发方案 NG-1](NEXT_GENERATION_PLAN.md)为准。本文保留资产流水线细节；正式显示已转向 Windows 游戏运行时串流。

本轮采用“一个高质量酒馆”验证完整产品链。现有参数化粗模只保留为开发调试工具，不作为正式世界视觉资产。暂停增加地形与区块数量，以当前应用里的真实体验验收。定时任务保持停止。

## 1. 用户只面对三个动作

1. **描述世界 → 创建**：例如“雨夜的湖边木制酒馆，暖色壁炉、旧橡木吧台，空间宽敞，可以绕到吧台后面”。可选附参考图，无需手工选择建模、贴图和烘焙工具。
2. **进入 → 自然语言调整**：准备完成后进入；“吧台向右移半米”“木头旧一些”“窗外改成傍晚”都转成局部事务，不重新生成整间酒馆。
3. **保存 / 导出**：自动保存场景版本；一键导出独立对象与贴图。再次进入直接加载固化内容。

默认不要求用户逐步确认设计、选供应商或修复模型。失败自动重试有界次数；无法达到质量门槛时展示明确失败及重试入口，不静默替换成色块粗模。设计参考图在准备区显示，不能冒充可游玩的三维画面。

## 2. 本轮具体场景

验证范围：约12×10米、单层、可进入的酒馆，门外小片庭院。包括吧台、壁炉、窗户、桌椅、木桶、酒架、瓶杯和灯具；暖色室内光与冷色窗外环境形成对比。尺度和数量为设计起点，可按布局校验调整。

需要能够：连续绕行、靠近观察、走到吧台背后、开门、拿起一个杯子；离开房间再返回位置不变。灯光变化可以延后精修，但不能阻塞移动。核心资产近看具有真实纹理密度、边缘细节与可信材质响应，而不是只在远景好看。

## 3. 主流程与每一步产物

### A. 管家编译场景意图

一次结构化模型调用，输出 SceneSpec：风格、米制空间边界、房间连接、功能区、行走通路、物件清单、材质族、光源意图、生成种子与必须保留的锚点。先检索资产目录的摘要，使计划只引用可解析的资产或明确的缺项。

设计参考图可复用现有世界模型产物；没有参考时，按同一 SceneSpec 生成一张总体设计图。参考生成与资源检索尽量并行，参考用于材质、造型和风格约束，不作为相机逐帧输出。不要再只提取五组RGB颜色。

输出：scene-spec.json、reference图及来源/哈希。已有世界从当前已提交的空间事实开始，不重新猜布局。

### B. 将物件清单变成资产任务

按“可复用 → 可改造 → 必须新生成”路由：

- 建筑：有实际厚度、接缝、倒角和完整材质的模块件，按约束确定性组装墙、梁、门窗、地板。
- 高频物件：从经验证、有授权的桌椅、酒桶、瓶杯库选择，复用网格与材质；实例变化由位置、尺度及有限材质参数实现。
- 特色物件：例如龙形酒馆招牌或雕花吧台正面，裁出对象级参考，再调用经实测的图像到3D/原生3D后端。
- 缺失装饰：可延迟加入，但不能把首次进入视野内的关键物件用低质替身交付。

首次验证优先建立一个小而完整的酒馆资产包。复用资产要标注来源；不能把它们说成模型现场生成。最终还必须完成至少一个特色物件的真实生成与入场，才能称生成到建模链路验证通过。

输出：AssetPlan，每项有稳定objectId、assetKey、route、优先级、尺寸/朝向、参考、预算与依赖。

### C. 生成 / 处理资产，合并成一个工作器阶段

外部后端只产生候选资产，统一工作器负责：单位与朝向校正、边界/枢轴、节点变换、材质解析、必要的拓扑清理与减面、UV检查、法线/切线、碰撞代理、LOD与导出。选择已有合格UV/拓扑的模型时跳过重复处理。

完整材质契约：baseColor、metallic-roughness、normal、AO、emissive及对应factor、UV集、sampler、alphaMode；baseColor/emissive与数据贴图区分色彩空间。无贴图的合法材质使用factor；有贴图但丢失必须报错。不能默认为木材，也不能对所有物体套同一法线。

生成参考上的阴影和高光不能直接当固有颜色烘进baseColor。材质去光照、无缝化和通道推断作为可选处理任务，产物要检验接缝、方向与通道语义。材质超分只用于确实缺乏清晰度的对象，同一材质族共用结果；它不能修复错误几何或替代真实材质通道。

输出：不可变资产包 asset.glb + material/images + collider + lod + provenance + validation。源模型、原贴图和优化运行包分开保存。

### D. 确定性组装与场景校准

用同一个 SceneManifest 管理渲染、碰撞、交互、保存、导出。单位米、Y向上；对象ID稳定；场景采用显式空间变换与材质绑定。校验门/墙/地板连接、物体穿插、出生点、通路净空及可交互对象可达性。

参考图用于比较构图、材质与风格；三维尺寸和关系以SceneSpec/用户校准为准。针对单张生成图无法确定的背面和遮挡区域，根据空间约束补全，明确这是重建/建模推断，不能宣称精确恢复原场景。

输出：版本化 manifest、对象与碰撞索引、固定验收相机轨迹。

### E. 光照准备与主视口加载

当前首选产品路径：**Windows 成熟游戏运行时 + 浏览器串流 + 后台资产处理**，对应第12节与NG-1。先验证UE5/Pixel Streaming以及打包后资产导入；保留session与对话外壳。原本地Three.js方案作为历史候选，不与正式运行时同时建设；不继续自写不完整的glTF解析器。

最低可进入条件：关键区域完整资产、PBR材质、环境照明/反射、主光源阴影、可用碰撞；后台再处理静态间接光和更精细的反射。静态间接光采用光照贴图或探针，动态物件继续用实时直接光与探针。木材/金属/玻璃必须有不同响应，灯具emissive本身不等于照亮周围。

Windows 5070 Ti 作为可替换的GPU工作器：生成、材质处理、可验证的烘焙/参考渲染。Falcor目前只有离线样张，不能假设已有光照贴图烘焙接口；先验证可用烘焙工具及UV2流程（例如Blender Cycles），再接入统一任务。没有烘焙时仍需完整实时PBR画面，质量状态明确显示为待精修。

光照贴图绑定和探针数据放在manifest扩展中，不能假设标准GLB会自动携带引擎专用光照。编辑物体或灯光只让相关光照结果失效；精修完成后平滑更新，不替换几何或重置相机。

不把远端PNG逐帧传输作为玩家控制通路；不以Lumen或DLSS NR作为本轮必需依赖。未来原生UE客户端/视频流是独立产品路线，不能暗中混入本轮延迟指标。

### F. 自动验收、固化和导出

验收通过后发布版本；已提交版本仍可用，生成/下载/校验失败不破坏它。运行时升级资源先下载解码，再在安全帧边界提交；玩家脚下的碰撞不得随视觉LOD变化。

导出两个包：运行包（压缩、LOD、实例与光照扩展），编辑包（独立对象GLB、原始贴图、碰撞JSON、manifest、来源清单）。用建模工具重新导入验证尺寸、材质、旋转与对象拆分。引擎特有光照应明确说明，不能承诺跨工具完全同样显示。

## 4. 加速策略：减少工作，而不是把全部任务并发启动

1. 内容寻址缓存：资产按参考hash + 生成器版本 + 参数/种子；处理结果按源资产hash + 工具版本 + 设置；光照按几何/材质/灯光/烘焙设置签名缓存。不能只按prompt字符串缓存。
2. 一个SessionPlanner，一套AssetWorker，一套SceneCompiler，一个Runtime。用户不直接操作内部服务；管家输出数据，固定工具执行，不实时生成状态机代码控制每次移动。
3. 同样assetKey的请求合并；失败步骤单独重试，已成功部分不重跑。超时/取消/重新进入都保留进度。
4. 一般装饰后台生成，关键物件优先；已经加载的可玩范围维持稳定。扩展先加载合格基础资产，再加入特色细节，不在玩家眼前刷新成另一张图。
5. 5070 Ti 先限制为一个重GPU任务，CPU下载/校验独立并行；基于峰值显存和实际耗时再增并发。不能假定16GB显存能同时运行重建、超分、烘焙与实时光追。
6. 网格实例化、按材质合理合批、LOD、视锥剔除、纹理mipmap/压缩和分批上传；避免把整座酒馆不可逆地合成一个网格。
7. 低分辨率生成预览只用于工作器内部筛选；进入玩家视口的材质必须满足观察距离的清晰度要求。压缩与降低分辨率分开处理。
8. 几何、材质、照明的编辑分别失效：移动杯子不重建房间；修改木纹不重做模型；改灯光不重做UV；扩展庭院不重新生成酒馆。

## 5. 三条时延必须分开测

以下是拟定工程目标，全部待真实酒馆测量，不是已有实测或所有硬件保证。

- **再次打开**：本地已有运行包，目标5秒内可进入。分别记录磁盘读取、解码、上传和首个可操作帧。
- **首次创建（资产库已准备，模型服务已热身）**：目标60–120秒内得到合格可游览酒馆；用检索/复用完成主体。首次下载资产库和安装环境另记，但不能从“全新机器首次体验”报告中隐去。
- **全新特色物件 / 精细光照**：单独记录模型排队、推理、处理、烘焙时延；目前无可信SLA。允许后台完成，不承诺秒级全新高质量3D生成。

帧率目标：先在**用户实际浏览器所在设备**以1920×1080、DPR=1固定测试，帧间隔P95≤20ms、区块接入不出现超过50ms的帧。逻辑输入每帧本地处理，不等待模型；报告RAF/CPU/GPU/网络各自范围，输入到显示延迟要另测。Windows GPU速度不是Mac浏览器帧率。

起始资源预算（可依据画质实测调整）：首屏运行包≤50MB，全部酒馆运行包≤150MB；纹理以共享1K/2K为主，近景特色资产按需提高；实时投影主灯先1–2盏。质量不达标时定位模型、材质或照明原因，不能只降分辨率换“通过”。

## 6. 首轮最小数据契约与模块落点

SceneSpec：sessionId、schemaVersion、seed、style、bounds、layout、anchors、assetRequests、lightingIntent。

AssetRecord：assetId、contentHash、provider/toolVersion、sourceReference、license、units、bounds、pivot、mesh/LODs、materials、collider、validation、qualityTier。

SceneManifest：sessionId、revision、parentRevision、objects(objectId/assetId/transform/materialOverrides/interaction)、lighting、dependencies、protectedRegions、spawn、buildStatus。

Job：id、inputHash、type、priority、state、dependencies、stageTimings、memoryPeak、resultHash、error、retryCount。状态 queued/running/validating/ready/failed/cancelled；世界版本只引用ready结果。

代码落点：

- `src/world-scene/service.ts`：当前“参考→Recipe→buildChunk”改为任务编排和版本发布；保留缓存/原子写入思想，不能沿用颜色Recipe作为最终场景契约。
- `src/world-scene/geometry.ts`：保留布局辅助和调试代理；正式视觉引用资产库，不由低面数原语替代。
- `src/server/graphics-service.ts`：沿用后端鉴权代理；补足资产上传、处理结果、能力与版本校验。离线Falcor能力和服务可调度能力分开。
- `src/server/public/app.html`：主视口加载正式PBR运行包；当前控制逻辑可复用。加入帧统计、资源版本与质量状态，不加入逐步技术配置表单。
- `src/exporter/`：保留原材质/贴图与节点身份，增加运行包和编辑包明确契约。
- Windows工作器：对象生成适配、标准化、材质/纹理处理、光照任务；源代码纳入版本管理，不以报告目录里的镜像充当部署源。

这是待实现设计；现有graphics接口只覆盖验证任务，没有以上全部能力。

## 7. 按可验收结果推进开发

### P0：主视口质量样板

先导入一套来源明确的高质量酒馆资产，在当前应用内跑通PBR、阴影、环境反射、碰撞和本地控制。这一步只验证显示链，明确资产来自库，不称世界模型生成。必须解决“远端好看、主视口仍是粗模”的断链后再做P1。

### P1：生成到组装

同一自然语言输入自动产生SceneSpec、资产路由与布局，构建能游玩的同风格酒馆。至少一个特色资产真正经过生成后端→三维处理→主视口。记录复用/生成比例与人工干预；尚无可用3D后端时明确该项阻塞，不能用手工样例替代通过。

### P2：局部编辑、精修和速度

实现“移动吧台”“修改木纹”“改变灯光”三种最小修改；只更新必要依赖。验证后台精修、缓存重开、断线恢复和新版本回滚。以实际trace确定瓶颈后优化，不盲目增加GPU任务数。

### P3：固化、离线与导出

停生成服务后仍可进入已固化酒馆、行走、开门、拿杯子；编辑包导入建模工具；门外追加庭院，室内已固化对象hash不变。此关通过后才恢复开放世界范围扩展。

## 8. 一次可复现的最终验收

固定6个近/中/远视角与60秒连续行走轨迹，覆盖地面接触、桌椅边缘、木纹近景、金属反射、窗光、壁炉、吧台背面。截图与录屏必须来自用户主视口；参考图与离线渲染单列。

分别执行至少3次冷创建（记录缓存状态）、5次缓存重开、三种局部编辑；记录端到端P50/P95时先说明样本数，少量样本只作初测，不形成稳定SLA。固定分辨率、设备、资产/模型/工具版本、种子、输入和渲染设置。

通过标准：没有丢贴图、错材质、黑屏、穿墙和视角切图；连续相机与稳定碰撞；无须手工修模型才能完成常规流程；状态可恢复；导出可编辑。画质还须由用户在真实主视口确认，测试数量或能力flag不替代审美验收。

最终报告逐项区分：代码检查通过、实际部署通过、视觉通过、性能通过、生成闭环通过、导出通过。任何一项未完成，不能笼统宣布“高质量酒馆方案已完成”。

这些文档支持工具选择，不证明本项目已部署这些能力。静态光照烘焙工具及生成后端还需实际环境验证。

## 10. Windows RTX 5070 Ti 分工（用户确认）

用户已明确同意将部分计算任务交给Windows N卡。资源分工如下：

- 本机：管家编排、世界版本与缓存、资源下载、客户端渲染、键鼠输入和碰撞。移动不跨网络等待。
- Windows CPU：资产校验、尺寸/UV/节点标准化、碰撞与LOD处理、纹理打包。不是所有建模步骤都能由GPU加速。
- Windows 5070 Ti：已验证后端支持的对象3D生成、材质去光照/超分、静态间接光烘焙、参考路径追踪。后三类任务按实际工具能力开放；当前不能将未部署的生成/烘焙功能标成可用。
- 现有世界模型服务：继续负责设计参考与内容提案，保留现有服务，不强制迁移到5070 Ti。

实施顺序：先让Carina场景资产能够上传到Windows并可靠取回处理结果；随后闭合材质/变换处理；再验证光照烘焙。缓存通过内容hash跨session复用，但用户私有资产沿用隔离权限。

GPU调度默认一个重任务，优先级：当前场景阻断任务 > 当前可见区域精修 > 下一房间预生成 > 远景预计算。已有任务取消/降级按工具支持处理，不承诺任意CUDA任务可抢占。显存准入按模型实测峰值+保留余量，显存不足延迟或降并发，禁止反复OOM重启。若未来同卡承担实时渲染，给帧预算优先级，后台任务只在可用余量内运行。

每个能力需要同时报告 installed、smokeVerified、jobRunnable；离线成功和能被Carina调度严格区分。输出携带inputHash、工具/模型版本、处理参数、阶段耗时、显存峰值、结果hash及语义说明（例如烘的是indirect而不是含直射光的combined），避免主视口重复叠加光照。

## 11. 建模与生成共存：空间稳定、外观可持续生成

2026-09-11补充：目标不是所有内容都人工精建模，也不是把世界模型逐帧输出覆盖游戏视口。采用混合表达，让生成结果成为可复用、可编辑、可版本化的世界资源。

### 三层表达

1. 空间/交互层：真实网格、米制坐标、碰撞、对象ID和状态，负责可走、可拿取、遮挡与导出。模型更新不能偷偷移动门、改变地板或改玩家脚下的碰撞。
2. 生成外观层：物体UV绑定的生成纹理、贴花、法线/粗糙度候选、静态光照贴图、环境贴图和探针。生成一次可被大量后续帧复用，不随玩家每次转头推理。
3. 远景/氛围层：天空、远山、受控范围内的图像代理，以及具备多视角证据时的Gaussian Splat候选；近处可交互部分仍需网格与碰撞。Splat是可选研究路径，不默认比网格省显存，也不能直接等同可编辑GLB。

### 生成画面如何变成上述资源

输入已有稳定几何→渲染带已知相机位姿的深度/法线/对象ID及参考视图→由支持这些条件的生成后端补充材质/细节→按可见性投影到对应对象UV→跨视角融合、接缝处理与不确定区域标记→输出PBR候选→主视口多视角检验→提交资源版本。

当前世界模型是否接受深度/法线/相机等条件必须实测；不支持时用它生成对象/材质参考，再由资产工作器加工，不能假称已经实现几何约束生成。单视图遮挡部分不能凭空当作已观测真值；用额外视角补充或明确生成补全。

光照单独处理：参考画面表达照明意图，用固定几何和实际灯光估计/重建一致的照明，烘焙静态间接光、保留动态直接光与阴影。直接投影带阴影的图片可以作为固定照明的外观缓存，但不应宣称可任意重打光的baseColor；高光和反射不能固定贴在表面。光照变化需使相关缓存失效，避免双重阴影。

### 边玩边生成的调度

按区域维护“候选→校验→可提交→已固化”状态，模型只修改候选。相邻区共享边界、材质风格和空间锚点；不每次独立从文字生成。按运动方向/速度预测到达时间，在可玩区域外提前生成；静态材质/光照缓存远比逐帧生成更适合复用。进入视野前完成高质量基础版本，后续仅分批、平滑替换外观资源；碰撞/拓扑变化单独做安全事务。预生成未完成时保留可信已知区域，不用随机画面伪装可进入空间。

### 速度与成本的判断

相对纯人工定制：生成纹理、特色装饰与初稿有望减少制作时间，但要把校准/修复时间算入。
相对成熟资产库实时渲染：生成和重建增加前处理成本，不天然省GPU；已有合格资产直接加载通常更快。
相对高细节全几何/逐帧高采样光追：把不影响轮廓/交互的细节放入纹理，将稳定间接光缓存，有机会降低每帧成本，但这是表示和缓存的收益，不是生成模型本身更便宜。
相对每帧世界模型推理：按资源变更触发、结果长期复用可显著减少推理次数；实际节省幅度需要测量。

酒馆最小A/B：保持布局、相机、分辨率和光源约束一致，A使用高质量资产库/标准材质，B以同几何加入生成材质、墙面细节与校准光照缓存。比较主视口多视角质量、总创建墙钟时间、人工分钟数、GPU秒/峰值显存、下载量、运行帧时、修改后重算量；单独记录生成失败/重试。不得只以B样张更精致推断它更快或更省资源。

参考边界：Neuralangelo从多视角图像重建表面，说明多视角几何证据的重要性（https://research.nvidia.com/labs/dir/neuralangelo/）；3DGS支持辐射场的实时新视角渲染，但不是普通可编辑网格（https://arxiv.org/abs/2308.04079）；Blender可分别烘焙颜色/直接/间接贡献，不能将混合光照误作固有颜色（https://docs.blender.org/manual/en/latest/render/cycles/baking.html）。以上研究不证明当前LingBot输出满足重建条件。

## 12. 用户接受远程游戏延迟：增加优先远程渲染路线

2026-09-11用户明确允许略高输入/输出延迟，以远程游戏体验为准。这更新第5节的路线约束：保留本地显示路径，但高质量酒馆验证可优先采用Windows实时运行/渲染、浏览器远程交互。不得将“允许延迟”解释为接受秒级模型等待或场景切图。

数据流：浏览器键鼠→低延迟输入通道→Windows固定步长控制/碰撞→稳定三维场景→光照/PBR（可选神经增强）→GPU视频编码→WebRTC传输→浏览器解码显示。场景与资产由后台任务异步修改，输入环不等待LLM；音视频与输入使用明确session绑定。

5070 Ti同时承担实时渲染与编码时，游戏帧预算优先。生成、超分和烘焙必须降低并发、暂停或安排在加载阶段；不能因为有独立编码单元就假设GPU/显存没有竞争。优先GPU表面直接编码，避免逐帧PNG和CPU读回；具体可用编码器及GPU互操作需要实际验证。

拟定而非已验证目标：先720p60确认链路，再1080p60；局域网输入到显示P50≤80ms、P95≤120ms作为初始验收目标，并测量抖动、丢帧与连续操作。真实输入到显示需外部高速录像或可校准方法验证；浏览器时间戳、网络RTT和服务端渲染耗时只能提供分段代理指标，不能冒充完整延迟。目标不含互联网/WAN保证，最终以用户体感与测量共同确认。

先用正常PBR/阴影的稳定场景打通编码与输入闭环，再增加间接光或真实可用的神经增强，并分别记录新增开销。DLSS5 NR尚未接入，不能将普通超分/去噪替代品命名为DLSS5。Windows资产仍需保存、编辑和导出，视频流仅是展示通道，不替代世界记忆。

失败行为：输入失焦/断连及时释放按键，序号丢弃过时输入；恢复连接重同步权威相机状态。服务认证沿用现有私有通道，媒体连通性、ICE候选和网络访问范围单独配置；不擅自暴露公网控制端口。
